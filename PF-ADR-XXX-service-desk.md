## 1. Проблема

Обращения партнёров МедФлекс сейчас вручную разбирают партнёрские менеджеры в личных ТГ-чатах, SLA не измеряется. Обращения нужно передать в техподдержку через структурированные задачи в Jira, но открыть партнёрам штатный портал Jira Service Management нельзя: ИБ запрещает публиковать Jira в интернет. Нужен отдельный сервис-прослойка: партнёр создаёт обращения и ведёт переписку, а внутренние комментарии и данные Jira не попадают к нему ни при каких условиях. В MVP — только партнёры МедФлекс; вход для МедЛок и ПроДокторов через SSO закладывается в архитектуру.

## 2. Варианты

Варианты взяты из 10 независимых проектов. Их сравнивали турниром: проекты атаковали друг друга и дорабатывались, а судья оценивал каждую пару по единой рубрике.

### Вариант 1: Опубликовать портал Jira Service Management

- **Суть:** открыть партнёрам штатный портал JSM из интернета.
- ✅ **Плюсы:** интерфейс, переписка и SLA уже готовы, разработки почти нет.
- ❌ **Минусы:** ИБ это прямо запрещает, потому что Jira становится доступной из интернета. Партнёрам понадобились бы учётки клиентов в Jira, а не логин, который выдаёт админка МедФлекса.

### Вариант 2: Прослойка с агентской учёткой Jira в DMZ

- **Суть:** сервис в DMZ ходит в Jira под учёткой агента и сам отфильтровывает внутренние комментарии.
- ✅ **Плюсы:** самый простой вариант: один процесс и полный доступ к API Jira.
- ❌ **Минусы:** при взломе процесса в DMZ утекают агентский секрет и все внутренние комментарии. Изоляция держится только на нашем фильтре. В турнире проекты с таким устройством проигрывали в том числе из-за этого.

### Вариант 3: Клиентская учётка JSM в DMZ, пароль проверяется в DMZ

- **Суть:**
  - в DMZ лежит только учётка с правами клиента JSM, и Jira сама не отдаёт ей внутренние комментарии;
  - агентская учётка есть только во внутреннем контуре;
  - пароль партнёра проверяется в DMZ по логину и хэшу «Пользователя ДМС»;
  - комментарий поддержки показывается партнёру, только если второй API Jira тоже считает его публичным.
- ✅ **Плюсы:** видимость комментариев проверяется двумя независимыми способами. Самый детальный проект по коду и краевым случаям.
- ❌ **Минусы:** процесс в DMZ читает логины и хэши паролей «Пользователей ДМС». При взломе их можно перебирать офлайн. Сложнее сопровождать.

### Вариант 4: Клиентская учётка JSM в DMZ, пароль и агентские операции во внутреннем контуре

- **Суть:**
  - как вариант 3, но в DMZ нет хэшей паролей: пароль проверяет внутренний процесс по узкому RPC из пяти методов;
  - роль БД портала видит только представление «активность + отпечаток хэша»;
  - у портала свой `SECRET_KEY` и своя таблица сессий;
  - три процесса: `portal` в DMZ, `internal` и `worker` во внутреннем контуре.
- ✅ **Плюсы:** при взломе процесса в DMZ не утекают ни агентский секрет Jira, ни внутренние комментарии, ни хэши паролей. Остаточные риски в проекте названы явно.
- ❌ **Минусы:**
  - вход зависит от внутреннего контура: если RPC недоступен, новые входы получают 503, уже вошедшие продолжают работать;
  - нет проверки видимости комментариев вторым API, которая есть в варианте 3;
  - три процесса и RPC вместо одного сервиса.

### Вариант 5: Без учёток Jira в DMZ (шлюз во внутреннем контуре)

- **Суть:** у процесса в DMZ нет ни учёток Jira, ни сетевого пути к ней. Все вызовы идут через шлюз во внутреннем контуре.
- ✅ **Плюсы:** минимальная поверхность атаки на Jira из DMZ.
- ❌ **Минусы:** появляется ещё один сервис и ещё одно звено в цепочке таймаутов. Шлюз работает под агентской учёткой, поэтому Jira не отсекает за нас внутренние комментарии, и изоляция держится на коде шлюза.

## 3. Решение

**Выбран вариант 4 — клиентская учётка JSM в DMZ, пароль и агентские операции во внутреннем контуре.** Почему: при взломе единственного публичного процесса злоумышленник получает не больше, чем партнёры и так видят по своим обращениям, и для этого не нужен отдельный шлюз. В финале турнира вариант 4 обошёл вариант 3 со счётом 84:83. Решающим доводом стали хэши паролей в DMZ у варианта 3; по детальности вариант 3 сильнее.

## 4. Последствия и следующие шаги

### Что меняется

- **Сервисы:** новый Service Desk — интерфейс на Vue 3 и бэкенд на Django/DRF в трёх процессах: `portal`, `internal`, `worker` (приложение А.2).
- **Деплой:** `portal` в DMZ, `internal` и `worker` во внутреннем контуре. Между `portal` и `internal` — mTLS (или сервисный токен) и сетевой ACL. Jira в интернет не публикуется.
- **БД:**
  - приложение `servicedesk` в БД МедФлекса; это допущение, оно зависит от устройства «Пользователя ДМС» (вопрос 1);
  - у `portal` и `internal` разные роли БД;
  - `portal` не видит таблиц МедФлекса и хэшей паролей.
- **Jira** (проект «МедФлекс: HELP», тип запроса «От сервиса-партнера»):
  - две технические учётки: клиент JSM для портала и агент с минимальными правами для `internal` и `worker`;
  - поля «Наименование партнера» и «Роль партнера» заполняет портал из доступа партнёра, партнёр их не видит;
  - форму типа нужно привести к согласованному списку полей (вопрос 3);
  - переход «Переоткрыть» из финальных статусов;
  - автоматизация не меняет статус, когда клиент оставляет комментарий.
- **Процессы:** поддержка отвечает партнёру «ответом клиенту» в Jira, внутренние комментарии партнёру не видны. Доступ партнёра заводят в новой админке service desk, а логин и пароль по-прежнему выдаёт админка МедФлекса.

### От чего отказываемся / какие риски принимаем

- Не публикуем JSM и не кладём агентскую учётку Jira в DMZ.
- Секрет клиентской учётки в DMZ даёт чтение публичной части всех обращений портала и создание запросов любого открытого типа в «МедФлекс: HELP». Риск принимает ИБ, либо партнёров выносим в отдельный сервис-деск (вопрос 4).
- Jira работает в одном экземпляре. Пока она недоступна, создание обращений и переписка не работают, список обращений открывается из БД портала. Синхронизация нагружает ту же ноду, её темп настраивается.
- Если `internal` недоступен, новые входы получают 503.
- Нет перекрёстной проверки видимости комментариев вторым API (вопрос 5).
- Поведение API Jira 10.3.5 не сверено с документацией Atlassian: проект опирается на описания Cloud API и клиентские библиотеки. Ключевые предположения проверяются на стенде до начала разработки (шаг 2).
- Обращения, заведённые в Jira вручную, в портале не видны.

## Приложение А. Устройство решения

### А.1 Схема

```
Партнёр (браузер)
   │ HTTPS
   ▼
Прокси / WAF ──► SPA (Vue 3)                                   [DMZ]
   │
   ▼
portal: API партнёра                                           [DMZ]
   │   Jira: только клиентская учётка JSM
   │   БД: роль без доступа к таблицам МедФлекса и хэшам паролей
   │
   ├── узкий RPC (mTLS) ──► internal                           [внутренний контур]
   │                          админка service desk,
   │                          проверка пароля, вебхуки Jira
   │
   └── клиентский API JSM ──► Jira DC 10.3.5 + JSM 10.3.5      [внутренний контур]
                              проект «МедФлекс: HELP»
                                    ▲
worker ─── агентская учётка ────────┘                          [внутренний контур]
   синхронизация статусов, сверки, письма

PostgreSQL: приложение servicedesk в БД МедФлекса              [внутренний контур]
```

### А.2 Компоненты

| Компонент | Где | Что делает | Доступы |
|---|---|---|---|
| SPA | DMZ, статика | Экраны по прототипу: вход, список, создание, карточка обращения | — |
| `portal` | DMZ | API партнёра: вход (через RPC), список, карточка, переписка, создание обращения, файлы | Клиентская учётка JSM; роль БД без доступа к таблицам МедФлекса |
| `internal` | Внутренний контур | Админка service desk, проверка пароля, RPC для `portal`, приём вебхуков Jira | Обе учётки Jira; чтение нужных колонок «Пользователя ДМС» |
| `worker` | Внутренний контур | Синхронизация статусов, досверка неподтверждённых записей в Jira, письма | Обе учётки Jira |
| Админка МедФлекса | Как сейчас | Выдаёт логин и пароль партнёра | Без изменений |
| Jira + JSM | Внутренний контур | Обращения, переписка, SLA | — |

### А.3 Что где хранится

- **В БД сервиса:**
  - доступы партнёров: ссылка на «Пользователь ДМС», название партнёра, роль, адреса для писем;
  - настройки продукта: привязка к Jira-проекту, мэппинг статусов, брендинг;
  - владение обращениями и снимок первого сообщения — поля формы так, как их отправил партнёр;
  - зеркало статусов для списка;
  - служебное: попытки создания, очередь писем, отметки синхронизации.
- **Не храним:**
  - тексты комментариев поддержки — каждый раз читаются из Jira;
  - набор и типы полей формы — берутся из Jira;
  - пароли и их хэши — пароль проверяет `internal` по данным МедФлекса.

### А.4 Основные сценарии

1. **Вход.** Партнёр вводит логин и пароль, выданные в админке МедФлекса. `portal` передаёт их в `internal` по RPC, и тот проверяет их по «Пользователю ДМС» и наличию доступа к service desk. Учётка одна на всех сотрудников партнёра. Смена пароля или отключение доступа сразу гасит все сессии.
2. **Создание обращения.**
   - Форма строится по схеме типа «От сервиса-партнера» из Jira.
   - При отправке сервис проверяет лимит: 3 обращения в минуту на партнёра, текст ошибки из постановки.
   - «Наименование партнера» и «Роль партнера» подставляются из доступа, заявку создаёт клиентская учётка.
   - Файлы уходят в Jira. Её лимит — 50 МБ на файл, ошибку Jira партнёр видит как есть.
   - Повторная отправка той же формы дубля не создаёт. Если ответ Jira потерялся, сервис сам выясняет, создана ли заявка.
3. **Список и статусы.** Список читается из БД сервиса и работает, даже когда Jira недоступна. Статус показывается по мэппингу из админки, отдельному для каждого продукта. Фильтр — только по статусу.
4. **Переписка.**
   - Комментарии читаются из Jira клиентской учёткой, и Jira отдаёт ей только публичные. Сервис дополнительно отбрасывает всё, что не помечено публичным.
   - Первое сообщение — поля формы с подписями.
   - Ответ партнёра становится публичным комментарием в Jira.
   - Закрытое обращение можно комментировать, статус от этого не меняется.
5. **Переоткрытие.** По кнопке «Переоткрыть» `internal` выполняет переход в Jira агентской учёткой. Если на стенде окажется, что переход доступен клиенту, его выполнит сам `portal`.
6. **Уведомления.** `worker` замечает новые внешние комментарии и отправляет партнёру одно письмо за 5 минут. Текст строки — из постановки.

### А.5 Безопасность

**Что гарантируется:**
- Jira не публикуется, наружу открыт только `portal`.
- Внутренние комментарии и их файлы не попадают к партнёру: Jira не отдаёт их клиентской учётке, а фильтры сервиса это дублируют. Скачать можно только файлы из разрешённого списка.
- Взлом `portal` не даёт агентского секрета Jira, внутренних комментариев, хэшей паролей и доступа к таблицам МедФлекса.
- Партнёр видит только свои обращения: владение хранится в БД сервиса и не вычисляется по полям Jira.

**Что остаётся** (решает ИБ):
- секрет клиентской учётки даёт чтение публичной части всех обращений портала и создание запросов в «МедФлекс: HELP»;
- одна учётка на партнёра без дополнительной защиты входа — осознанное решение продукта;
- если на стенде клиентская учётка не сможет работать через REST API, останется только агентская учётка во внутреннем контуре, а изоляция станет слабее.

| Статусы | Набор статусов зависит от типа задачи, в который попадает «От сервиса-партнера». Мэппинг строится по нему |

### А.7 Задел на будущее

- **SSO МедЛок и МедТочки:** новый способ входа подключается к той же модели учётки без переделки ядра.
- **Несколько продуктов:** каждый продукт привязывается к своему Jira-проекту со своим мэппингом статусов. Проекты МедЛок, ПроДокторов и МедТочки в Jira уже есть.
- **Мультибрендинг:** логотип и тема на продукт задаются в админке. В MVP бренд один — МедФлекс.

| API | Application Programming Interface | Программный интерфейс; здесь — HTTP-API Jira и API портала |
| auth | authentication / authorization | Аутентификация и авторизация (вход и права) |
| БД | база данных | — |
| Data Center | — | Self-hosted редакция Jira, которая ставится на свои серверы (в отличие от Cloud) |
| DMZ | Demilitarized Zone | Сегмент сети, доступный из интернета и отделённый от внутренней сети |
| DRF | Django REST Framework | Библиотека для REST API на Django |
| ДМС | обычно «добровольное медицинское страхование» | «Пользователь ДМС» — существующая сущность МедФлекса; точный смысл в её кодовой базе не проверен |
| ИБ | информационная безопасность | — |
| JSM | Jira Service Management | Модуль Jira для служб поддержки: портал, клиенты, SLA |
| MVP | Minimum Viable Product | Первая минимальная версия продукта |
| mTLS | mutual TLS (Transport Layer Security) | Шифрованное соединение, в котором сертификаты проверяют обе стороны |
| Нода | — | Один работающий экземпляр (сервер) Jira. Data Center может работать кластером из нескольких нод, у нас нода одна |
| ОРИ | — | Расшифровка в постановке не дана |
| QA | Quality Assurance | Обеспечение качества; здесь — QA-инженеры, которых хотят разгрузить |
| REST | Representational State Transfer | Стиль HTTP-API, в котором работает API Jira |
| RPC | Remote Procedure Call | Удалённый вызов; здесь — внутренние HTTP-вызовы `portal` → `internal` |
| `SECRET_KEY` | — | Секретный ключ Django для подписи сессий и токенов |
| SLA | Service Level Agreement | Соглашение об уровне сервиса; здесь — сроки реакции и решения обращений |
| SPA | Single Page Application | Веб-интерфейс, который работает в браузере и обращается к API |
| SSO | Single Sign-On | Единый вход через внешнюю систему авторизации (SSO МедЛок, SSO МедТочки) |
| ТГ | Telegram | — |
| Тип запроса | request type (JSM) | Форма обращения в JSM с собственным набором полей; у нас — «От сервиса-партнера» |
| WAF | Web Application Firewall | Фильтр HTTP-запросов перед приложением |
| Агент / клиент (JSM) | — | Роли в JSM: агент — сотрудник поддержки, видит всё, включая внутренние комментарии; клиент — заявитель, видит только публичное |
