## 1. Проблема

Ошибки и запросы партнёров МедФлекс сейчас разбирают партнёрские менеджеры вручную, в личных ТГ-чатах. Обращения не структурированы, их нельзя посчитать, SLA не измеряется, менеджеры перегружены. Нужно, чтобы партнёр сам создавал структурированное обращение, видел его статус и переписывался с поддержкой, а техподдержка работала с ним в Jira как с обычной задачей. Штатный портал Jira Service Management для этого не подходит: ИБ запрещает публиковать Jira в интернет. В MVP — только партнёры МедФлекс; клиники МедЛок и пациенты ПроДокторов подключатся позже.

## 2. Варианты

### Вариант 1: Открыть партнёрам портал Jira Service Management

- **Суть:** опубликовать штатный портал JSM в интернет и завести партнёров клиентами JSM.
- ✅ **Плюсы:** интерфейс, переписка, статусы и SLA уже есть, разработки почти нет.
- ❌ **Минусы:**
  - ИБ это прямо запрещает: Jira становится доступной из интернета;
  - партнёрам нужны учётки клиентов в Jira, а не логин, который выдаёт админка МедФлекса.

### Вариант 2: Форма и почта без своего портала

- **Суть:** партнёр заполняет внешнюю форму (как сейчас в Яндекс.Формах «Ошибки партнёров»), форма создаёт заявку в Jira, переписка идёт по почте через почтовый канал JSM.
- ✅ **Плюсы:** быстро и дёшево, своего сервиса нет.
- ❌ **Минусы:**
  - у партнёра нет списка обращений и статусов, нет кнопки «Переоткрыть»;
  - поля формы зашиты в саму форму, а не берутся из Jira;
  - партнёр не идентифицируется логином из админки МедФлекса, «Название сервиса» и «Роль» не подставляются автоматически;
  - большая часть требований постановки не выполняется.

### Вариант 3: Свой портал поверх клиентского API JSM

- **Суть:** свой веб-сервис с входом по логину из админки МедФлекса. Обращения и комментарии сервис создаёт в Jira через клиентский API JSM, поддержка работает в Jira как обычно, SLA считает JSM.
- ✅ **Плюсы:**
  - выполняются все требования постановки: список и фильтр по статусу, понятные партнёру статусы, структурированное первое сообщение, вложения, переоткрытие, письма;
  - Jira остаётся закрытой;
  - поддержка не меняет инструмент, SLA считает сама Jira;
  - тот же сервис подключит МедЛок и ПроДокторов: другой Jira-проект и другой способ входа.
- ❌ **Минусы:**
  - новый сервис, который нужно разработать и сопровождать;
  - синхронизация с Jira: статусы и комментарии появляются у партнёра с задержкой, сбои Jira нужно обрабатывать;
  - сервис зависит от клиентского API JSM нашей версии; его поведение проверяется на стенде до разработки.

## 3. Решение

**Выбран вариант 3 — свой портал поверх клиентского API JSM**, технически — одно веб-приложение (Django/DRF и Vue 3) и Celery. Почему: это единственный вариант, который выполняет требования постановки и не открывает Jira; поддержка остаётся в Jira, а SLA начинает считаться автоматически. Как устроен сервис — приложение А, как обеспечена изоляция от Jira — приложение Б.

## 4. Последствия и следующие шаги

### Что меняется

- **Сервисы:** новый Service Desk — веб-приложение (интерфейс на Vue 3, бэкенд на Django/DRF) и Celery (worker и beat) с брокером Redis. Письма Celery отправляет через почтовую подсистему Django (SMTP).
- **Деплой:**
  - nginx и веб-приложение — в DMZ; Celery и Redis — во внутреннем контуре;
  - из DMZ открыт доступ только к PostgreSQL, Redis (с паролем) и клиентскому API Jira, а также к API МедФлекса, если вход будет сверяться через него (вопрос 2);
  - Celery нужен доступ к SMTP-серверу;
  - админка service desk (`/sd-admin/`) доступна только из внутренней сети или VPN.
- **БД и вход:** «Пользователь ДМС» хранится в МедФлексе. Как сверять логин и пароль — через представление в БД МедФлекса или через API МедФлекса — открытый вопрос 2. От ответа зависит, где лежат таблицы service desk (А.3): в БД МедФлекса или в своей БД.
- **Jira** (проект «МедФлекс: HELP», тип запроса «От сервиса-партнера»):
  - привести поля типа к списку постановки (А.7): убрать «Ссылку на клинику» и «МИС», Приоритет скрыть со значением по умолчанию;
  - добавить служебное текстовое поле «Ref портала» (А.4);
  - служебные поля «Наименование партнера», «Роль партнера» и «Ref портала» оставить в типе видимыми: по всей видимости, клиентская учётка не может заполнять скрытые поля (проверяется на стенде, А.14). Партнёру сервис эти поля не показывает;
  - завести две технические учётки: клиента JSM для веб-приложения и агента с минимальными правами для Celery;
  - настроить переход «Переоткрыть» из финальных статусов;
  - выключить автоматизацию, которая меняет статус по комментарию клиента;
  - выключить уведомления JSM для технической учётки клиента: письма партнёрам шлёт сервис.
- **Процессы:**
  - менеджер, выдав партнёру логин в админке МедФлекса, заводит ему доступ в админке service desk (А.5, сценарий 1);
  - поддержка отвечает партнёру «ответом клиенту» в Jira, а файлы для партнёра прикладывает к такому ответу;
  - любые изменения типа «От сервиса-партнера» в Jira согласуются с командой сервиса: от них зависит форма у всех партнёров;
  - порядок подключения партнёров и перевод переписки из ТГ-чатов решают продукт и менеджеры; в этот ADR это не входит.

### От чего отказываемся / какие риски принимаем

- Не публикуем JSM и не пользуемся его порталом.
- **Задержка.** Статусы и комментарии поддержки появляются у партнёра с задержкой до 2 минут (в открытой карточке — через несколько секунд), письма — до нескольких минут (А.12).
- **Зависимость от настроек Jira.** Если в типе «От сервиса-партнера» удалят поле или добавят обязательное поле неподдерживаемого типа, создание обращений остановится у всех партнёров. Сервис это обнаружит и поднимет алерт.
- **Общий проект.** «МедФлекс: HELP» используют и другие отделы. Его workflow и автоматизации влияют на обращения партнёров.
- **Одна нода Jira.** Пока Jira недоступна, создавать обращения и переписываться нельзя; вход и список обращений работают.
- **Непроверенный API.** Ключевые предположения о клиентском и агентском API JSM 10.3.5 не сверены с документацией Atlassian и проверяются на стенде до разработки (А.14).
- **Обращения, заведённые в Jira вручную,** в портале не видны.
- **Остаточные риски безопасности** приняты; они перечислены в приложении Б.

## Приложение А. Устройство сервиса

### А.1 Кто чем пользуется

| Роль | Где работает | Что делает |
|---|---|---|
| Сотрудник партнёра | Портал | Создаёт обращения, смотрит статусы, переписывается, переоткрывает. Учётка одна на весь партнёр |
| Партнёрский менеджер | Админка МедФлекса, админка service desk | Выдаёт логин и пароль; заводит доступ к service desk: название партнёра, роль, адреса для писем (вопрос 1) |
| Техподдержка МедРокет | Jira | Работает с обращениями как с обычными задачами JSM; отвечает «ответом клиенту» |
| Администратор service desk | Админка service desk | Привязка к Jira-проекту, мэппинг статусов, брендинг, наблюдение за сбоями |
| Администратор Jira | Jira | Настройка проекта, типа запроса, учёток, workflow |

### А.2 Схема

```
Партнёр (браузер)                 Сотрудник МедРокет (внутренняя сеть / VPN)
   │ HTTPS                                   │
   ▼                                         ▼
nginx ──────────────────────────────────────────────────────────  [DMZ]
   │  /, /api/v1/ — из интернета;  /sd-admin/ — только изнутри
   ▼
Веб-приложение (Django/DRF + SPA на Vue 3)                         [DMZ]
   │  Jira: только клиентская учётка JSM
   │
   ├── клиентский API JSM ──► Jira DC 10.3.5 + JSM 10.3.5          [внутренний контур]
   │                          проект «МедФлекс: HELP»
   │                                ▲
   └── задачи (только id) ──► Redis │                               [внутренний контур]
                                │   │ агентская учётка
                                ▼   │
                         Celery worker + beat ──► SMTP (письма)     [внутренний контур]

PostgreSQL: таблицы service desk (в БД МедФлекса или своей — вопрос 2)
«Пользователь ДМС»: в МедФлексе (сверка через БД или API — вопрос 2)
```

| Компонент | Что делает |
|---|---|
| nginx | HTTPS, статика интерфейса, проксирование в веб-приложение; к админке пускает только изнутри |
| Веб-приложение | API портала, вход, админка service desk. В Jira ходит клиентской учёткой: создать обращение, прочитать и написать комментарий, загрузить и скачать файл |
| Celery worker и beat | Всё фоновое и всё, что требует агентской учётки: синхронизация статусов, вторая проверка комментариев, переоткрытие, досверка, письма, кэш участников групп |
| Redis | Брокер очереди Celery |
| PostgreSQL | Данные сервиса (А.3) |
| SMTP-сервер | Доставка писем партнёрам |

### А.3 Модель данных

**Где что хранится.** Jira — источник правды о содержании: поля обращения, комментарии, файлы, статус, исполнитель. Сервис хранит только то, что Jira не знает или что нужно без Jira: кто владелец обращения, как его показать партнёру, настройки.

| Сущность | Что хранит | Зачем |
|---|---|---|
| Продукт | Код, название, хост портала, адрес для ссылок в письмах, способ входа | Несколько продуктов на одном сервисе: МедФлекс сейчас, МедЛок и ПроДокторов потом |
| Привязка к Jira | Проект, сервис-деск, основной тип запроса, поля «Наименование партнера», «Роль партнера» и «Ref портала», переход «Переоткрыть», статус по умолчанию | Один продукт — один Jira-проект |
| Статус партнёра | Подпись, цвет, порядок, признак «закрыт» | Понятные партнёру статусы, свои для каждого продукта |
| Мэппинг статусов | Статус Jira (по id) → статус партнёра | Партнёр не видит внутренних статусов Jira |
| Брендинг | Логотип, подписи, цвета темы | Задел на несколько брендов; в MVP — МедФлекс |
| Доступ партнёра | Ссылка на «Пользователя ДМС», название партнёра, роль, адреса для писем (вопрос 1), активность | Кто может входить и что подставлять в Jira |
| Обращение | Ссылка на задачу Jira (id и ключ), владелец, снимок первого сообщения, зеркало статуса, даты, предупреждения | Список без Jira, первое сообщение не зависит от изменений в Jira |
| Попытка создания | Ключ повтора, маркер «Ref портала», состояние (создаётся / создано / отказ / неизвестно), введённые значения до завершения | Лимит 3 в минуту, защита от дублей, поиск потерянных обращений |
| Отправка комментария | Ключ повтора, состояние | Защита от дублей комментариев |
| Увиденный комментарий | Id комментария Jira, кто автор, подтверждена ли публичность, отправлено ли письмо | Показ только проверенных комментариев, письма без повторов |
| Неопознанная заявка («сирота») | Задача технической учётки без владельца | Алерт и ручная привязка |
| Состояние синхронизации | Отметка последнего успешного опроса Jira | Не терять изменения после простоя |
| Кэш участников групп | Имена сотрудников для поля выбора пользователя | Поле выбора работает без агентской учётки в вебе |

Своей таблицы логинов и паролей нет: доступ ссылается на существующего «Пользователя ДМС». Где лежат таблицы сервиса — в БД МедФлекса или в своей — зависит от вопроса 2.

### А.4 Интеграция с Jira

**Две учётки:**
- **Клиент JSM** — у веб-приложения. Всё, что делает партнёр: создать обращение, прочитать и написать комментарий, загрузить и скачать файл. Jira отдаёт клиенту только публичные комментарии, а в Jira его действия выглядят как действия клиента, поэтому SLA JSM работает по смыслу.
- **Агент с минимальными правами** — только у Celery. Чтение статуса, исполнителя и дат; чтение комментариев — только для второй проверки публичности; переход «Переоткрыть»; поиск задач для синхронизации и по маркеру «Ref портала».

**Вторая проверка комментариев.** Jira сама не отдаёт клиенту внутренние комментарии. Дополнительно Celery проверяет каждый новый внешний комментарий агентской учёткой: Jira должна подтвердить его публичность и через агентский API. Пока проверка не прошла, партнёр комментарий не видит и письмо о нём не уходит; обычно это несколько секунд. Если два ответа Jira расходятся, комментарий остаётся скрытым и поднимается алерт.

**Синхронизация.** Источник правды — Jira, у сервиса только зеркало для списка и фильтра.
- Каждые 2 минуты Celery запрашивает задачи проекта, изменённые с момента последнего успешного опроса. Поэтому после простоя ничего не теряется.
- Раз в час — полная сверка свежих обращений, раз в сутки — всех.
- Когда партнёр открывает карточку, обращение обновляется сразу, а новые комментарии сразу уходят на вторую проверку.
- Вебхуки Jira не используются: опроса достаточно.

**Сбои Jira:**

| Что вернула Jira | Что видит партнёр |
|---|---|
| Отказ (неверные поля, слишком большой файл) | Ошибку Jira у поля или у файла; ничего не создано, лимит не тратится |
| Нет ответа или ошибка сервера при создании | «Не удалось подтвердить создание. Проверяем — результат появится в списке». Celery ищет заявку по маркеру «Ref портала»; повторная отправка дубля не создаст |
| Jira недоступна | «Сервис временно недоступен»; введённые данные сохраняются |
| Задача удалена или перенесена | Обращение остаётся в списке с пометкой; при переносе ссылки не ломаются, потому что сервис хранит id задачи, а не ключ |

**Поиск потерянных обращений.** Каждая попытка создания получает уникальный маркер, сервис записывает его в служебное поле «Ref портала». Если ответ Jira на создание потерялся, Celery ищет задачу по точному совпадению маркера и привязывает её к партнёру. По теме или названию партнёра обращение не привязывается: так можно отдать его чужому партнёру. Если поиск по маркеру не заработает (А.14), неподтверждённые создания разбирает администратор вручную в админке. Раз в час Celery также ищет задачи технической учётки без владельца («сироты») и поднимает алерт.

### А.5 Сценарии

1. **Заведение партнёра.**
   - Менеджер создаёт логин и пароль в админке МедФлекса и передаёт их партнёру через сервис передачи секретов (как сейчас).
   - В админке service desk менеджер создаёт доступ: выбирает «Пользователя ДМС», вводит название партнёра, выбирает роль из списка ролей Jira, вводит адреса для писем (вопрос 1).
   - Партнёр входит в портал.
2. **Вход.** Логин и пароль сверяются с «Пользователем ДМС» в МедФлексе (способ — вопрос 2), затем проверяется активный доступ. Неверная пара — «Неверный логин или пароль». Нет доступа — «Доступ к службе поддержки не выдан. Обратитесь к партнёрскому менеджеру». Регистрации и восстановления пароля нет.
3. **Создание обращения.**
   - Форма сразу открывает тип «От сервиса-партнера», без выбора типа.
   - Поля строятся по схеме из Jira (А.7), файлы — перетаскиванием.
   - При отправке: проверка полей, лимит 3 обращения в минуту с текстом из постановки, подстановка «Наименование партнера», «Роль партнера» и маркера «Ref портала». Значения служебных полей от партнёра не принимаются.
   - Успех — переход в карточку. Файл не прикрепился — обращение создано, в карточке плашка «прикрепите файл в переписке».
4. **Список.** Все обращения партнёра, независимо от того, кто из сотрудников их создал. Сортировка по последнему видимому партнёру изменению. Фильтр только по статусу. Работает и без Jira.
5. **Карточка и переписка.**
   - Первое сообщение — поля формы с подписями, файлы под ним.
   - Дальше только внешние комментарии, прошедшие вторую проверку (А.4), с ролью «МедРокет» или «Партнёр» и файлами.
   - Справа — исполнитель, номер, статус, даты.
   - Ответ партнёра становится публичным комментарием в Jira. Повторная отправка после обрыва связи дубля не создаёт.
6. **Закрытое обращение.** Баннер «Обращение закрыто» с кнопкой «Переоткрыть» и поле ответа. Комментарий статус не меняет. Кнопка ставит задачу в Celery, партнёр видит «Переоткрываем…», статус обновляется через несколько секунд.
7. **Уведомления** — А.11.
8. **Отключение партнёра.** Менеджер выключает доступ в админке service desk — сессии партнёра гаснут на следующем запросе. Смена пароля в админке МедФлекса тоже должна завершать сессии; как сервис об этом узнаёт, зависит от вопроса 2. Обращения сохраняются.

### А.6 Статусы

- Партнёру показываются четыре статуса: **Открыт, В работе, Ожидает вас, Закрыт** (решено).
- Мэппинг строится по id статуса Jira, поэтому переименование статуса в Jira его не ломает. Настраивается в админке отдельно для каждого продукта.
- Статус Jira без мэппинга показывается как статус по умолчанию, а админка его подсвечивает.
- Признак «закрыт» включает баннер и кнопку «Переоткрыть».

**Черновик мэппинга для «МедФлекс: HELP».** Финально настраивается в админке вместе с поддержкой. Статусы взяты из проекта; какие из них реально встречаются у типа «От сервиса-партнера», зависит от его workflow.

| Статус партнёра | Статусы Jira |
|---|---|
| Открыт | Открыт |
| В работе | В процессе; В работе у QA, у 1С, у Механикум, у проджект-менеджера, у продакт-менеджера; Передано в разработку; Передано интеграторам; Mech: Передано разработчикам Python, 1C; Ожидание техподдержки; Ожидание информация от внешнего сервиса |
| Ожидает вас | Ожидание информации; Ожидание партнёра; Ожидание автора; Request Info |
| Закрыт | Закрыт; Закрыто; Фича; Не воспроизводится; Внешняя ошибка; Задача добавлена в Backlog |

«Задача добавлена в Backlog» в черновике отнесена к «Закрыт». Если партнёру важно видеть, что ошибку взяли в доработку, её можно перенести в «В работе» в админке, без разработки.

### А.7 Форма обращения

**Поля типа «От сервиса-партнера»** — по постановке (решено):

| Поле | Обязательное |
|---|---|
| Кратко опишите проблему | да |
| Что вы пытались сделать? | да |
| Какой результат ожидали? | да |
| Какой результат получили? | да |
| Curl-запрос | нет |
| Какой ответ API получаете? | нет |
| Дата появления ошибки | да |
| Файл (вложение) | нет |

- Служебные поля партнёр не видит:
  - «Наименование партнера» и «Роль партнера» подставляются из доступа партнёра;
  - «Ref портала» — маркер попытки создания;
  - Приоритет скрыт со значением по умолчанию, поддержка меняет его сама.
- «Ссылка на клинику» и «МИС» из типа убираются.
- Предлагается сделать «Кратко опишите проблему» системным полем «Тема» (Summary): из него берутся заголовок в списке и тема в письмах.
- Часть полей можно не создавать, а переиспользовать (приложение В).

**Схема формы** (решено):
- Набор и типы полей не хранятся в сервисе: веб-приложение берёт схему типа из Jira и кэширует её на 5 минут.
- При отправке схема перечитывается. Если она изменилась, форма перерисовывается, введённые значения сохраняются.
- Поддерживаемые типы полей: текст, многострочный текст, ссылка, число, дата, дата и время, выпадающий список, множественный выбор, радиокнопки, флажки, каскадный список, метки, выбор пользователя, вложения.
- Выбор пользователя ограничен Jira-группой, заданной в админке; список её участников Celery кэширует раз в 15 минут.
- Неподдерживаемое поле: необязательное скрывается, обязательное блокирует форму с сообщением «Создание обращений временно недоступно», админка показывает причину.
- Старые обращения показываются по снимку первого сообщения: удаление или изменение типа в Jira их не ломает.
- Новый тип запроса в Jira не меняет форму: партнёру открывается тип, выбранный в админке. Шаг выбора типа вернётся отдельной задачей.

### А.8 API портала

| Метод | Назначение |
|---|---|
| `POST /auth/login`, `POST /auth/logout`, `GET /me` | Вход, выход, кто вошёл |
| `GET /branding` | Логотип и тексты продукта, без входа |
| `GET /statuses` | Статусы для фильтра |
| `GET /request-types`, `GET /request-types/{id}/form` | Тип обращения и схема формы |
| `GET /form/user-search` | Поиск для поля выбора пользователя |
| `POST /tickets` | Создать обращение (с файлами и ключом повтора) |
| `GET /tickets`, `GET /tickets/{id}` | Список и карточка |
| `GET /tickets/{id}/comments`, `POST /tickets/{id}/comments` | Переписка и ответ партнёра |
| `POST /tickets/{id}/reopen` | Переоткрыть (через Celery) |
| `GET /tickets/{id}/attachments/{attId}` | Скачать файл |

- Все ошибки — в одном формате JSON с текстом для партнёра.
- Чужое обращение по любому адресу — 404.
- Служебные поля в схему формы для партнёра не попадают, а их значения в запросе партнёра отклоняются.

### А.9 Экраны

Экраны повторяют прототип. Отличия от него:
- **Вход:** только логин и пароль; логотип и подписи из брендинга.
- **Список:** статусы фильтра приходят из API, фильтр сохраняется в адресе страницы; счётчик с правильным склонением; пустые состояния.
- **Создание:** карточки выбора типа нет, форма открывается сразу. Подсказку «до 20 файлов, 20 МБ» из прототипа не хардкодим: лимит берётся из Jira. Черновик текста сохраняется в браузере.
- **Карточка:** у закрытого обращения показываются и баннер, и поле ответа (в прототипе поле ответа скрыто, а постановка требует обратного). «Исполнитель» — исполнитель из Jira, «Дата решения» — дата решения из Jira.
- **Мобильная ширина** — как в прототипе.

### А.10 Админка service desk

| Раздел | Что внутри |
|---|---|
| Доступы | «Пользователь ДМС», название партнёра, роль (выбор из списка Jira), адреса для писем (вопрос 1), активность. Пароль здесь не создаётся |
| Продукт и привязка Jira | Проект, основной тип запроса, поля автоподстановки, поле «Ref портала», переход «Переоткрыть». Кнопка «Проверить подключение» |
| Статусы | Статусы партнёра и мэппинг; немапленные статусы Jira подсвечены |
| Брендинг | Логотип, подписи, цвета |
| Наблюдение | Неподтверждённые создания (ручная привязка к задаче или «не создано»), «сироты», комментарии, не прошедшие вторую проверку, отставание синхронизации, письма без адресатов, недоступная форма |

### А.11 Уведомления

- **Повод** — новый внешний комментарий поддержки. Свои комментарии партнёра и смена статуса писем не вызывают.
- **Агрегация:** первое событие открывает для партнёра окно на 5 минут; всё, что пришло за это время, попадает в одно письмо.
- **Текст** — по строке на каждое обращение, дословно из постановки: «В запросе №[номер] «[тема]» есть обновление. Ссылка для перехода: [ссылка]».
- **Отправка** — Celery, через почтовую подсистему Django (SMTP).
- **Почему не уведомления JSM:** JSM пишет заявителю, а заявитель у всех обращений портала — одна техническая учётка. Поэтому уведомления JSM для неё выключены, а письма шлёт сервис.
- **Адресаты** — вопрос 1. Без адресов письмо не теряется: остаётся в очереди, админка показывает проблему.
- Перед отправкой Celery проверяет, что комментарий всё ещё существует и прошёл вторую проверку.

### А.12 Нефункциональные требования

| Что | Значение |
|---|---|
| Объём | Меньше сотен тысяч обращений, точной оценки нет. Опроса Jira раз в 2 минуты для этого достаточно |
| Задержка статусов и комментариев | До 2 минут; в открытой карточке — несколько секунд на вторую проверку |
| Задержка писем | До ~8 минут от комментария: синхронизация, окно 5 минут, такт планировщика |
| Лимит создания | 3 обращения в минуту на партнёра |
| Файлы | До 50 МБ на файл (лимит Jira); nginx пропускает тело запроса не меньше 51 МБ |
| Без Jira | Работают вход и список; не работают создание и переписка |
| Нагрузка на Jira | Опрос раз в 2 минуты и ограниченная по темпу полная сверка раз в час |

### А.13 Наблюдаемость и эксплуатация

- **Логи** пишут id, а не содержимое полей, комментариев и файлов.
- **Алерты:**
  - синхронизация отстала больше чем на 15 минут;
  - появилась «сирота» или обращение, которое не удалось подтвердить;
  - комментарий не прошёл вторую проверку;
  - Jira отвечает ошибкой авторизации (сломалась учётка);
  - форма недоступна (неподдерживаемое обязательное поле, пропала опция роли);
  - письма не уходят (SMTP недоступен) или у партнёра нет адресатов;
  - статус Jira без мэппинга.
- Резервные копии — в составе БД, где лежат таблицы сервиса (вопрос 2).

### А.14 Проверки на стенде до разработки

| Что проверяем | Если не подтвердится |
|---|---|
| Клиентская учётка работает через REST API JSM: создание, комментарии, файлы до 50 МБ | Переписку читает и пишет Celery агентской учёткой; изоляция слабее (Б.2) |
| Клиентская учётка может заполнить видимые служебные поля при создании | Название и роль Celery дописывает агентской учёткой сразу после создания. Маркер «Ref портала» тогда не работает, неподтверждённые создания разбираются вручную |
| Скрытый Приоритет со значением по умолчанию подставляется при создании через API | Сделать Приоритет необязательным для типа |
| Агентский API отдаёт признак публичности комментария | Вторая проверка ловит только ограничения видимости по ролям и группам; первый слой (права клиента) остаётся |
| Задача находится по значению «Ref портала» | Неподтверждённые создания разбирает администратор вручную |

### А.15 Запуск

1. **Подготовка:** настройка Jira, проверки на стенде (А.14), финальный мэппинг статусов с поддержкой.
2. **Разработка:**
   - модели, админка, интеграция с Jira;
   - создание обращения и переписка;
   - синхронизация, вторая проверка комментариев, письма;
   - фронтенд параллельно, на заглушках API.
3. **Внутренний тест** на тестовом партнёре: обращения доходят, поддержка отвечает из Jira, письма приходят, SLA считается.
4. **Подключение партнёров** — по плану продукта и менеджеров, вне этого ADR.

## Приложение Б. Безопасность

### Б.1 Что гарантируется

- Jira не публикуется: из интернета доступны только nginx и веб-приложение.
- Внутренние комментарии и их файлы не попадают к партнёру. Слоёв три:
  - Jira не отдаёт их клиентской учётке;
  - веб-приложение отбрасывает всё непубличное;
  - Celery подтверждает публичность каждого комментария агентской учёткой (А.4).

  Скачать можно только файлы проверенных комментариев.
- Агентская учётка Jira есть только у Celery во внутреннем контуре.
- Партнёр видит только свои обращения: владение хранится в БД сервиса. Служебные поля (название партнёра, роль, маркер) заполняет сервис, партнёр их подменить не может.
- Админка service desk доступна только из внутренней сети.

### Б.2 Принятые риски

- **Взлом веб-приложения даст:**
  - хэши паролей партнёров с доступом к service desk — если вход сверяется через представление БД; при проверке через API МедФлекса хэшей у веб-приложения нет (вопрос 2);
  - права админки service desk;
  - чтение публичной части всех обращений портала и создание запросов в «МедФлекс: HELP».
- **Очередь Celery** — граница доверия: задачи принимают только id и сами проверяют права; сообщения только в JSON; Redis с паролем.
- **Учётка партнёра** — одна на всех его сотрудников, без дополнительной защиты входа. Это осознанное решение продукта.
- **Предел второй проверки:** обе проверки читают одну Jira. Если сотрудник по ошибке напишет внутреннюю информацию ответом клиенту, партнёр её увидит. Это вопрос процесса поддержки, а не интеграции.
- **Если на стенде окажется,** что клиентская учётка не работает через REST API, переписку придётся читать агентской учёткой через Celery. Изоляция станет слабее.

### Б.3 Как выбирали схему изоляции

Устройство изоляции сравнивали турниром из 10 независимых проектов. Сравнивались схемы:

| Схема | Суть | Итог |
|---|---|---|
| 1 | Агентская учётка Jira в DMZ, фильтр только наш | Отклонена: при взломе утекают все внутренние комментарии |
| 2 | Клиентская учётка в DMZ, пароль проверяется в DMZ, плюс перекрёстная проверка комментариев | Финалист |
| 3 | Клиентская учётка в DMZ, пароль и агентские операции — в отдельном внутреннем процессе | Победитель турнира, 84:83 против схемы 2 |
| 4 | Шлюз во внутреннем контуре, в DMZ нет учёток Jira | Запасной вариант, если клиентская учётка не работает через REST |
| 5 | Одно веб-приложение и Celery | **Выбрана после турнира** как упрощение схемы 3: меньше частей. Из схемы 2 взяты перекрёстная проверка комментариев и маркер «Ref портала». Цена — хэши паролей партнёров и админка в процессе, открытом в интернет (Б.2). В турнире не сравнивалась |

## Приложение Г. Сокращения и термины

| Сокращение | Расшифровка | Что значит в этом ADR |
|---|---|---|
| ADR | Architecture Decision Record | Запись об архитектурном решении |
| API | Application Programming Interface | Программный интерфейс; здесь — HTTP-API Jira, API портала и, возможно, API МедФлекса |
| auth | authentication / authorization | Аутентификация и авторизация (вход и права) |
| БД | база данных | — |
| Брокер | — | Хранилище очереди задач между веб-приложением и Celery; у нас Redis |
| Вторая (перекрёстная) проверка | — | Подтверждение агентской учёткой, что комментарий, который Jira отдала клиенту, действительно публичный |
| Celery | — | Система фоновых задач для Python/Django. Worker выполняет задачи, beat запускает их по расписанию |
| Data Center | — | Self-hosted редакция Jira, которая ставится на свои серверы (в отличие от Cloud) |
| DMZ | Demilitarized Zone | Сегмент сети, доступный из интернета и отделённый от внутренней сети |
| DRF | Django REST Framework | Библиотека для REST API на Django |
| ДМС | обычно «добровольное медицинское страхование» | «Пользователь ДМС» — существующая сущность МедФлекса; точный смысл в её кодовой базе не проверен |
| Досверка | — | Выяснение, создалась ли в Jira заявка, на которую не пришёл ответ |
| ИБ | информационная безопасность | — |
| JSM | Jira Service Management | Модуль Jira для служб поддержки: портал, клиенты, SLA |
| Мэппинг статусов | — | Соответствие «статус Jira → понятный партнёру статус» |
| MVP | Minimum Viable Product | Первая минимальная версия продукта |
| nginx | — | Веб-сервер перед веб-приложением: HTTPS, статика, проксирование, ограничение доступа по адресам |
| Нода | — | Один работающий экземпляр (сервер) Jira; у нас нода одна |
| ОРИ | организатор распространения информации в сети Интернет | Статус по 149-ФЗ (ст. 10.1) с обязанностью хранить данные и предоставлять их через СОРМ. Для сервиса не требуется |
| QA | Quality Assurance | Обеспечение качества; здесь — QA-инженеры, которых хотят разгрузить |

| «Ref портала» | — | Служебное поле Jira с уникальным маркером попытки создания; по нему находится обращение, если ответ Jira потерялся |
| REST | Representational State Transfer | Стиль HTTP-API, в котором работает API Jira |
| «Сирота» | — | Задача в Jira от технической учётки, у которой в сервисе нет владельца |
| Снимок первого сообщения | — | Поля формы так, как их отправил партнёр; хранится в сервисе и показывается первым сообщением |
| SLA | Service Level Agreement | Соглашение об уровне сервиса; здесь — сроки реакции и решения обращений |

| ТГ | Telegram | — |

| VPN | Virtual Private Network | Защищённый доступ во внутреннюю сеть |
| Агент / клиент (JSM) | — | Роли в JSM: агент — сотрудник поддержки, видит всё, включая внутренние комментарии; клиент — заявитель, видит только публичное |
