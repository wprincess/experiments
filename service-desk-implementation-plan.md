## 1. Цель и критерий готовности

**Цель** — MVP из ADR (приложение А.16): партнёры МедФлекс работают с обращениями через свой портал, поддержка — в Jira.

**MVP готов, когда в проде:**
- партнёр входит по логину и паролю из МедФлекса;
- создаёт обращение «От сервиса-партнера» с файлами;
- видит список обращений с фильтром по статусу;
- переписывается с поддержкой и может переоткрыть закрытое обращение;
- получает письма о новых ответах;
- поддержка отвечает из Jira, а SLA в Jira считается;
- внутренний тест на тестовом партнёре пройден, ИБ провела ревью.

**Не входит в план:** подключение реальных партнёров и перевод их из ТГ-чатов (решают продукт и менеджеры), SSO МедЛок и МедТочки, шаг выбора типа обращения.

## 5. Этапы подробно

### Этап 0. Подготовка и проверки на стенде

**Задачи:**
- **Администратор Jira:**
  - решить, где проверяем: отдельный стенд Jira или тестовый проект в боевой Jira;
  - настроить тип запроса и проект по чек-листу (раздел 6);
  - завести технические учётки: клиента JSM и агента с минимальными правами.
- **Команда с администратором Jira:** пройти проверки из раздела 7 и записать по каждой результат и выбранный путь.
- **Разработка МедФлекса:** согласовать контракт API проверки логина и пароля:
  - что возвращает (минимум «верно / неверно», желательно id пользователя);
  - как авторизуется сервис;
  - тестовый адрес.
- **DevOps:**
  - окружения (локальное, стенд, прод);
  - заявки на сетевые доступы: DMZ → PostgreSQL, Redis, клиентский API Jira, API МедФлекса; внутренний контур → Jira, SMTP;
  - SMTP-релей;
  - доступ к `/sd-admin/` только из внутренней сети или VPN.
- **Продукт и поддержка:** финальный мэппинг статусов (черновик — ADR А.6).
- **ИБ:** срок хранения снимков и логов.

**Готово, когда:** есть протокол проверок, тип запроса на стенде настроен, контракт API МедФлекса записан, заявки на доступы поданы.

### Этап 1. Каркас

**Задачи:**
- Репозиторий: Django и DRF, настройки по окружениям, секреты только из окружения.
- Своя БД PostgreSQL, миграции.
- Celery worker и beat, брокер Redis с паролем, сериализация только JSON.
- docker-compose для локальной разработки: PostgreSQL, Redis, мок SMTP.
- CI: линтер, форматтер, тесты.
- Клиент Jira:
  - клиентская учётка — для веб-приложения;
  - агентская — только для Celery: её секрета нет в окружении веб-приложения;
  - исходы вызовов делятся на три вида: отказ Jira, неизвестный исход, Jira недоступна.
- Моки для тестов: Jira и API МедФлекса.
- Контракт API портала (OpenAPI) по ADR А.8 с единым форматом ошибок. Публикуется сразу, по нему стартует фронтенд.
- Проверки работоспособности веб-приложения и Celery для мониторинга.

**Готово, когда:** сервис разворачивается локально и на стенде, CI зелёный, OpenAPI опубликован.

### Этап 2. Вход и админка

**Задачи:**
- **Модели:** Продукт, Привязка к Jira, Статус партнёра, Мэппинг статусов, Брендинг, Доступ партнёра (ADR А.3).
- **Данные по умолчанию:** продукт МедФлекс и четыре статуса — Открыт, В работе, Ожидает вас, Закрыт.
- **Вход:**
  - клиент API МедФлекса с таймаутами;
  - проверка активного доступа;
  - сессия с ограниченным сроком (срок — `<TODO>`, выбрать до начала этапа);
  - новый ключ сессии и CSRF-токен после входа.
- **Методы API:** выход, `/me`, `/branding`.
- **Тексты ошибок входа** — из ADR А.5, сценарий 2, включая «Вход временно недоступен», если МедФлекс не отвечает.
- **Выключение доступа:** сессии партнёра гаснут на следующем запросе.
- **Админка** — отдельный сайт на `/sd-admin/`:
  - доступы: логин МедФлекса, название партнёра, роль из списка Jira, адреса для писем, активность;
  - привязка к Jira с кнопкой «Проверить подключение»;
  - статусы и мэппинг, немапленные статусы подсвечены;
  - брендинг.
- **Задел под SSO:** способ входа хранится у продукта; ядро не ветвится по способу входа.

**Готово, когда:** проходят тесты входа (верная пара, неверная, нет доступа, МедФлекс недоступен, выключение доступа → 401); менеджер заводит доступ в админке.

### Этап 3. Форма и создание обращения

**Задачи:**
- **Схема формы:**
  - загрузка схемы типа из Jira, сопоставление типов полей Jira с виджетами формы;
  - кэш 5 минут, перечитывание при отправке; при изменении — ответ «схема изменилась» с новой схемой;
  - служебные поля («Наименование партнера», «Роль партнера», «Ref портала») в схему для партнёра не попадают;
  - неподдерживаемое необязательное поле скрывается, обязательное делает форму недоступной и даёт сигнал в админку.
- **Поле выбора пользователя:** поиск только среди участников группы; кэш участников обновляет Celery раз в 15 минут.
- **Создание обращения:**
  - проверка полей;
  - лимит 3 обращения в минуту на партнёра, атомарно, с дословным текстом: «Достигнут лимит на создание запросов. Повторите, пожалуйста, отправку запроса через 1 минуту»;
  - ключ повтора: повторная отправка не создаёт дубль;
  - маркер «Ref портала»;
  - автоподстановка названия и роли партнёра; их значения от партнёра отклоняются;
  - вложения до 50 МБ на файл;
  - снимок первого сообщения.
- **Неизвестный исход:** попытка переходит в «неизвестно»; Celery ищет задачу по маркеру «Ref портала».
- **«Сироты»:** раз в час Celery ищет задачи технической учётки без владельца.

**Готово, когда:** обращение из API появляется в Jira с правильными полями. Проходят тесты: лимит при параллельных запросах, ключ повтора, все типы полей, автоподстановка, изменение схемы, неизвестный исход, «сирота».

### Этап 4. Список, синхронизация, карточка, переписка

**Задачи:**
- **Синхронизация (Celery):**
  - опрос раз в 2 минуты задач, изменённых с последнего успешного опроса; отметка сдвигается только после успеха;
  - сверка свежих обращений раз в час и всех раз в сутки;
  - обновление обращения при открытии карточки.
- **Статусы:** мэппинг статусов; статус Jira без мэппинга показывается статусом по умолчанию и подсвечивается в админке.
- **Список:** фильтр по статусу, сортировка по последнему видимому изменению; работает без Jira.
- **Карточка:** первое сообщение из снимка, исполнитель, номер, статус, даты.
- **Комментарии:**
  - чтение клиентской учёткой, отбрасывание всего непубличного;
  - вторая проверка в Celery агентской учёткой; пока проверки нет, комментарий скрыт; если ответы расходятся — комментарий скрыт и поднимается алерт.
- **Ответ партнёра:** публичный комментарий с ключом повтора, вложения к ответу. В закрытом обращении ответ статус не меняет.
- **Файлы:** скачивание только из первого сообщения и проверенных комментариев.
- **Переоткрытие:** задача Celery выполняет переход «Переоткрыть»; партнёр видит «Переоткрываем…».

**Готово, когда:** проходят тесты:
- чужое обращение по любому адресу → 404;
- внутренний комментарий и его файл не видны;
- после простоя Celery изменения не теряются;
- ответ в закрытом обращении не меняет статус;
- двойное переоткрытие безопасно.

### Этап 5. Письма

**Задачи:**
- **Повод** — новый внешний комментарий поддержки, прошедший вторую проверку.
- **Окно 5 минут** на партнёра: одно письмо со строкой на каждое обращение. Текст дословно: «В запросе №[номер] «[тема]» есть обновление. Ссылка для перехода: [ссылка]».
- **Отправка** через почтовую подсистему Django (SMTP) из Celery.
- **Без адресатов** письмо остаётся в очереди, админка показывает проблему.
- **Перед отправкой** — проверка, что комментарий существует и прошёл вторую проверку.

**Готово, когда:** проходят тесты из раздела 8 про письма; на стенде письмо приходит в тестовый ящик.

- **Очистка** снимков и логов по сроку, согласованному с ИБ.

**Готово, когда:** каждый алерт воспроизведён на стенде и дошёл до канала алертов.

## 6. Чек-лист настройки Jira (для администратора)

   | Файл | нет | Вложение |

   «Ссылка на клинику» и «МИС» убрать. Приоритет скрыть со значением по умолчанию. Можно переиспользовать существующие поля: «Дата возникновения ошибки» (`customfield_15110`), «Шаги воспроизведения» (`customfield_10345`), «Фактический результат» (`customfield_10346`).
2. **Служебные поля** «Наименование партнера» (`customfield_14004`, текст), «Роль партнера» (`customfield_14005`, список) и новое текстовое поле «Ref портала» включены в тип **видимыми**. Их id вносятся в админку service desk.
3. **Клиентская учётка** — клиент этого сервис-деска. Самостоятельная регистрация клиентов выключена. Уведомления JSM для этой учётки выключены.
4. **Агентская учётка** — роль поддержки только в `MFHELP`. Права: Browse Projects, Transition Issues; Edit Issues — только если проверка 2 из раздела 7 не пройдёт. Если в форме будет поле выбора пользователя — право читать участников группы. Лицензию уточняет администратор Jira.
5. **Переход «Переоткрыть»** из каждого финального статуса, без обязательных полей на экране перехода. Id перехода вносится в админку.
6. **Автоматизации,** меняющие статус по комментарию клиента, выключены — как минимум для закрытых статусов.
7. **Вложения** включены, лимит 50 МБ.
8. **Заявки от клиентской учётки вручную не создаются:** сервис считает все такие заявки своими и поднимает алерт «сирота».
9. **Изменения типа** «От сервиса-партнера» согласуются с командой сервиса: от них зависит форма у всех партнёров.

## 9. Работа с ИИ-агентами

Реализация планируется с помощью ИИ-агентов, поэтому:

- **Одна задача агенту — один пункт этапа:** с критерием готовности и тестами из раздела 8. Агенту дают ADR, этот план и нужный раздел детального проекта.
- **Поправки к детальному проекту.** Он написан под схему с тремя процессами (`portal`, `internal`, `worker`). Для агента это переводится так:
  - `portal` и `internal` — одно веб-приложение; админка в нём же, на `/sd-admin/`;
  - вызовы `internal` по RPC становятся задачами Celery; вход — вызовом API МедФлекса;
  - представления БД МедФлекса и ролей БД под него нет: своя БД, пароли не хранятся;
  - вебхуков Jira нет, только опрос;
  - вторая проверка комментариев и маркер «Ref портала» — обязательны.
- **Тесты на инварианты до кода:** видимость, чужие данные, лимит, ключ повтора.
- **Обязательное ревью человеком:**
  - всё, что касается видимости комментариев и файлов;
  - проверка владельца обращения;
  - использование агентской учётки (только Celery);
  - вход и сессии;
  - логи (без паролей и содержимого).

## 10. Риски плана

| Риск | Что делаем |
|---|---|
| Нет отдельного стенда Jira | Тестовый проект в боевой Jira; договориться с поддержкой, чтобы тестовые заявки не мешали |
| Проверки на стенде дают отрицательный результат | Включаем запасные пути из раздела 7; объём этапов 3–4 растёт |
| API МедФлекса готов позже бэкенда | Вход на заглушке, интеграция перед этапом 8; риск сдвига запуска |
| Детальный проект написан под другую схему | Поправки из раздела 9; спорные места решает ведущий программист |
| Агентская учётка требует платного места | Учесть в бюджете до этапа 0 |
| Изменения типа запроса в Jira во время разработки | Изменения типа только через команду сервиса (раздел 6, п. 9) |
